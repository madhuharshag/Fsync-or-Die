# Team Innovexa — Fsync-or-Die (`kip`)

[![Go Version](https://img.shields.io/badge/Go-1.23%2B-00ADD8?style=flat&logo=go)](https://go.dev/)
[![Correctness](https://img.shields.io/badge/Correctness-Crash--Proof-success)](#the-invariant)

An embedded, single-process, crash-resilient key-value storage engine and command-line interface written in Go for the **"Kill It and Prove It"** 24-Hour Engineering Hackathon.

---

## 1. Overview & Problem Statement

Database engines that only operate under ideal conditions provide zero real-world value. In real environments, operating system processes are terminated unexpectedly (`kill -9`, Win32 `TerminateProcess`, hardware power faults), leaving disk structures torn or half-written.

**Fsync-or-Die (`kip`)** guarantees that:
1. Every acknowledged write or atomic batch that returned success is durable and permanently recoverable after an abrupt crash.
2. Incomplete or torn mutations are cleanly detected via dual CRC32 checksums, rolled back, and truncated without corrupting prior history.
3. Recovery replays 1,000,000 keys in well under 2 seconds.

---

## 2. The Core Invariant

After a crash at any arbitrary instruction and subsequent restart:
1. **Durability:** Every operation that returned success before the kill is present with exact bytes.
2. **Atomicity:** Every atomic batch is treated as a single indivisible unit—it is either 100% present or 0% present. Never partially visible.
3. **Integrity:** No key ever holds corrupted or garbage bytes.
4. **Self-Healing:** Database recovery (`open`) succeeds deterministically on any file generated by the engine, repairing incomplete torn tails without administrative intervention.

## 3. Architecture Summary

### Storage Engine Layout (Little-Endian)
The authoritative database state resides in a single binary file (`<path>.kip`):

```
+-----------------------------------------------------------------------+
| File Header (32 Bytes): Magic "KIPDB001", Version, MaxFileBytes, CRC  |
+-----------------------------------------------------------------------+
| Transaction 1: Header (32B) -> Payload [Ops] -> Commit Footer (32B)   |
+-----------------------------------------------------------------------+
| Transaction 2: Header (32B) -> Payload [Ops] -> Commit Footer (32B)   |
+-----------------------------------------------------------------------+
| ...                                                                   |
+-----------------------------------------------------------------------+
```

- **TxnHeader (32B):** Magic `"TXN1"`, Version, Flags, TxID (uint64), OpCount (uint32), PayloadLen (uint64).
- **Operations:** Compact little-endian records: `[Kind: 1B][KeyLen: 2B][ValLen: 4B][Key][Value]`.
- **CommitFooter (32B):** Magic `"COMMIT01"`, TxID, TotalTxBytes, TxnCRC (IEEE CRC32 over header + payload), FooterCRC.
- **Process Mutual Exclusion:** Process-level exclusion is maintained on `<path>.lock` via native Win32 `LockFileEx` (Windows) and POSIX `flock` (Linux/macOS).

## 4. Building & Running

### Requirements
- Go toolchain `1.23` or higher.
- Native Windows 11 / Linux (Ubuntu/Debian) / macOS.

### Single Build Command
```bash
go build -o kip ./cmd/kip
```
*(On Windows PowerShell: `go build -o kip.exe ./cmd/kip`)*

Alternatively, run directly with Go:
```bash
go run ./cmd/kip <command> [args...]
```

## 5. Command-Line Reference (The Mandatory 8 Commands)

All 8 commands specified in Section 6 of the hackathon challenge are fully implemented:

```bash
# 1. Open or create database, run crash recovery, and display key count & recovery duration
./kip open <db-path> [--max-bytes N]

# 2. Durably write key-value pair (prints ACK <key> on confirmed fsync)
./kip put <db-path> <key> <value>

# 3. Retrieve value (prints raw value, or NOTFOUND with exit code 2)
./kip get <db-path> <key>

# 4. Durably delete key (prints ACK <key>)
./kip del <db-path> <key>

# 5. Atomically commit batch of operations from file (JSON array or line-based format)
./kip batch <db-path> <file>

# 6. Verify full physical file integrity, transaction boundaries, and dual CRCs
./kip check <db-path>

# 7. Print all live key-value pairs sorted lexicographically by key
./kip dump <db-path>

# 8. Interactive stdin/stdout IPC mode used by crash torture harnesses
./kip serve <db-path> [--max-bytes N]
```

### Additional Administrative Commands:
```bash
# Display live engine telemetry (LiveKeys, FileSize, MaxCapacity, LastTxID)
./kip stats <db-path>

# Trigger crash-safe atomic space reclamation (compaction)
./kip compact <db-path>

# Display reference manual
./kip help
```

For complete syntax, exit codes, and JSON schemas, see [`docs/CLI_USAGE.md`](docs/CLI_USAGE.md).

## 9. Limitations & Failure Boundary

- **Power-Loss Protection:** While our write path calls physical `fsync` (`FlushFileBuffers`), survival under unbuffered write-cache power loss depends on drive hardware honouring flush barriers.
- **Full-Capacity Deletions:** When the file is at 100% capacity (`committedEnd >= maxFileBytes`), append-only delete tombstones return `ErrFull`. Compaction must be triggered to reclaim space.
- **Bit Rot:** Mid-file bit-rot on inactive records is detected upon running `kip check <db-path>`, but is not self-healing without replica logs.
